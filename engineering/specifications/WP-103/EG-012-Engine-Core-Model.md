# EG-012 — Engine Core Model

- Work Package: WP-103
- Increment: 1
- Status: Draft
- Version: 0.1.0
- Target release: SIF Builder 2.0.0-alpha1
- Depends on: EG-011, WP-101

## 1. Objective

Implement the immutable core model required by the Builder Engine without introducing orchestration, extension registries, repository discovery, artifact writing, or reporting adapters.

This increment establishes the public vocabulary used by later WP-103 increments: requests, execution policy, lifecycle phases, immutable context snapshots, diagnostics, stage results, terminal results, and the engine contract.

## 2. Scope

This increment includes:

- `BuilderEngineInterface`;
- `BuilderRequest`;
- `BuilderContext`;
- `BuilderPhase`;
- `BuilderStatus`;
- `ExecutionPolicy`;
- `Diagnostic` and `DiagnosticSeverity`;
- immutable `DiagnosticCollection`;
- `StageResult`;
- `BuilderResult`;
- validation exceptions;
- unit tests.

## 3. Exclusions

The following remain deferred:

- analyzer and generator contracts;
- extension registries;
- lifecycle transition orchestration;
- repository discovery and indexing stages;
- generated artifact model and writing;
- statistics and reporters;
- CLI or CI adapters.

## 4. Namespace

```text

```

A future governed namespace consolidation is outside this increment.

## 5. Core invariants

### 5.1 Builder request

A request:

1. has a non-empty normalized repository root;
2. may define a normalized output root;
3. uses a lowercase governed execution profile;
4. selects `STRICT` or `LENIENT` execution policy;
5. preserves analyzer and generator selection order;
6. rejects duplicate extension identifiers after normalization;
7. contains no services or mutable registries.

### 5.2 Builder context

A context:

1. has a stable run identifier;
2. starts in a governed phase;
3. exposes scalar, sorted configuration values;
4. creates a new instance when phase, configuration, or index changes;
5. does not expose the mutable internal `RepositoryIndex` instance directly;
6. remains suitable for future analyzer and generator consumption.

The repository index is cloned on input and output. This provides an immutable snapshot boundary without changing the existing WP-101 domain object.

### 5.3 Diagnostics

A diagnostic:

- has a stable uppercase code such as `ENGINE-001`;
- has one of `INFO`, `WARNING`, `ERROR`, or `FATAL` severity;
- contains a non-empty human-readable message;
- may identify a source and extension;
- contains only scalar or null safe context;
- may include a remediation hint;
- serializes without throwable objects or arbitrary internal data.

Diagnostics are deterministically ordered by:

1. severity descending;
2. code;
3. source;
4. extension;
5. message.

### 5.4 Terminal result

A terminal result:

- is immutable;
- contains a unique ordered list of completed phases;
- derives clean or diagnostic success status through its factory;
- requires a safe summary when failed;
- may retain a throwable cause in memory;
- never serializes the throwable cause;
- serializes stable diagnostic counts.

## 6. Lifecycle values

```text
CREATED
PREPARING
DISCOVERING
INDEXING
ANALYZING
GENERATING
FINALIZING
COMPLETED
FAILED
```

Transition validation is intentionally deferred to Increment 3. Increment 1 only establishes the governed values and terminal-state query.

## 7. Execution policy

```text
LENIENT
STRICT
```

Policy behavior is defined by EG-011 and will be implemented by the pipeline in Increment 3. The core model stores the selected policy without executing it.

## 8. Public contract

```php
interface BuilderEngineInterface
{
    public function run(BuilderRequest $request): BuilderResult;
}
```

No concrete engine is included in this increment.

## 9. Determinism

The following are deterministic:

- normalized request paths and identifiers;
- configuration key order;
- diagnostic order;
- completed phase order supplied by the engine;
- JSON field structure and diagnostic counts.

Runtime timing, random identifiers, and environment-derived values are not generated by this model.

## 10. Safety

The model rejects:

- empty governed identifiers;
- null bytes in paths;
- duplicate requested extensions;
- invalid diagnostic codes;
- nested or object diagnostic context;
- nested or object configuration values;
- duplicate completed phases;
- failed results without a safe summary.

Throwable stack traces and messages are not serialized automatically.

## 11. Acceptance criteria

The increment is accepted when:

1. all source files comply with PHP 8.2 and PSR-12;
2. requests normalize valid Windows and Unix-style paths;
3. contexts return immutable copies when enriched;
4. repository index state cannot be mutated through the context boundary;
5. diagnostics validate and serialize safe structured data;
6. diagnostic collections are immutable and deterministically ordered;
7. stage success is derived from diagnostic severity;
8. terminal results retain but do not serialize causes;
9. PHPUnit passes;
10. PHPStan level 8 passes;
11. Composer resolves `Sif\Builder\Engine\` through the approved PSR-4 mapping;
12. the complete existing test suite remains green.
